1. **A focused fullscreen window covers a top-layer surface that has the keyboard; with exclusive interactivity this traps the keyboard.** **checked** `src/view.c:269`, focus, confidence high.

2. **The memfd and posix_fallocate protection in shmalloc.c is tied to the wlroots version check and goes away with 0.19.3 or 0.20.2.** **checked** `src/main.c:961`, nohacks, confidence high.

   shmalloc.c does two separate jobs. It works around the missing wlr_buffer_finish() in 0.19.2, which upstream fixed in 4279ee5 for 0.19.3. It also makes buffers with memfd_create() and posix_fallocate() instead of shm_open() in /dev/shm, so that a buffer larger than what is free in /dev/shm is not a SIGBUS on first touch (shmalloc.c:13-17). Both depend on '#if WLR_VERSION_NUM < 0.19.3' at main.c:961. wlroots' util/shm.c still uses shm_open() plus ftruncate() in 0.19.3 and in 0.20.2 (checked with git show 0.20.2:util/shm.c). So a build against 0.19.3, or the 0.20 move that TODO:67-70 plans ('src/shmalloc.c fällt dann weg'), brings the SIGBUS back. Example: the Podman image from tests/Containerfile has a 64 MiB /dev/shm by default. Run mwc there headless with pixman and a 3840x2160 output, as for wayrdp or wayvnc, where one buffer is about 33 MB. The second swapchain buffer, or a screencopy buffer, runs out of tmpfs pages, and mwc dies with SIGBUS on the first frame. The memfd part is a design choice, not a workaround for a wlroots bug, yet it is removed together with the bug fix.

   [Suggested: Decide on the memfd allocator separately from the wlroots bug. Either keep it outside the version check as mwc's own allocator for the shm case (drop only the 'before 0.19.3' wording and keep the wlr_buffer_finish, which does no harm on fixed versions), or let it go on purpose and add the /dev/shm limit for headless and container setups to CAVEATS.md. In either case, correct TODO's 'src/shmalloc.c fällt dann weg'.]

   [Decided: shmalloc.c stays as mwc's own allocator for the shm case, without the version check; its comment and TODO say why.]

3. **Maximized/snapped/fullscreen windows jump to another monitor when their output shrinks (scale or mode change).** **checked** `src/view.c:1110`, outputs, confidence high.

   Outputs A (1920x1080 at 0,0) and B, with B placed by wlroots (add_auto) to A's right. On A there is a fullscreen window (x=0, width 1920) or a window snapped to the right half (x=960, width 960). wlr-randr or outputc sets A to scale 2, or to a mode with half the width (3840x2160 to 1920x1080). A becomes 0..960 x 0..540 and wlroots moves B to x=960. layout_change runs layer_arrange for each output, which calls views_usable_area_changed and view_refit, and then views_layout_changed. Both look up the output by the window's centre: the fullscreen window at (960,540), the right half at (1440,540). That point is now on B, so output_full_area and snap_area return B's box. The fullscreen window covers B, and the right-half window becomes B's right half; neither stays on A. With an explicit outputPosition for B (a gap after the shrink), the centre is on no output, and output_at() falls back to the newest output in the layout, often B. A maximized window behaves the same as soon as a top or left panel moves its centre past A's new edge. 'reachable' is true in every case, so nothing keeps the window on A.

   [Suggested: Remember the output a state window was fitted to, for example a wlr_output pointer set in view_fit_state() and in the fullscreen paths, cleared when that output is destroyed or leaves the layout. Neither the centre nor the largest intersection works here: the right-half window no longer overlaps A at all. A test for outputs.sh: two auto-placed outputs, a window snapped right and one fullscreen on the left output, 'outputc apply LEFT scale 2', then check that both are on the left output.]

4. **Opaque resize of an X11 window sends a ConfigureWindow for every pointer motion; the xdg throttle was never extended to X11.** `src/input.c:478`, performance, confidence medium.

   With moveOpaque: true, drag the corner of an X11 window that has no resize increments (Firefox or LibreOffice under Xwayland, GIMP 2, an Electron app with X11 forced) using a 1000 Hz mouse. process_resize() only defers xdg windows: `else if (view->type == VIEW_XDG && configure_serial < anchor_serial) grab_resize_waiting = true; else resize_to(view, &target);`. For VIEW_XWAYLAND, resize_to() calls view_set_geometry() and so wlr_xwayland_surface_configure() whenever the target changes, which is every pixel of motion. wlroots 0.19.2 (xwayland/xwm.c:2112) does not dedupe: each call is an xcb_configure_window plus a flush. Each request resizes the X window server-side, so Xwayland reallocates the window's composite pixmap and the client gets a ConfigureNotify for each one. Every resulting commit also hits xw_commit() -> frame_render() (4 cairo buffers and a Pango title). Up to about 1000 window resizes a second reach the X server, far more than the client can draw, and the window lags behind the pointer. This is the cost Review 2026-11-14 item 11 described, fixed in 75c3260 for xdg only. The TODO entry on X11 resize jitter covers where the window is placed, not this rate.

   [Suggested: Use the same catch-up gate for X11. In process_resize(), while the last configured size hasn't been committed yet (view->xsurface->width/height != view->width/height), set grab_resize_waiting instead of calling resize_to(). In xw_commit(), after view->width/height are updated, call grab_resize_caught_up(view) once s->current matches xsurface->width/height. end_grab() already applies a waiting target, so the final size isn't lost if the client never redraws. A test in tests/move.sh with xclient and `vinput glide` could count configures, as the feedback test counts draws.]

5. **xdg min_size is not capped: INT32_MAX minimum overflows the tiling layout, resize outline and placement.** **checked** `src/hints.c:155`, robustness, confidence high (also found by hostile).

   An xdg client sends xdg_toplevel.set_min_size(2147483647, 2147483647) and leaves max at 0. wlroots 0.19.2 only checks that the values are >= 0 and max >= min (types/xdg_shell/wlr_xdg_toplevel.c:124), so the value passes. read_xdg_size_hints() copies it into view->min_w/min_h unchanged, unlike X11 (hint_size(), 32767) and unlike the committed geometry (size_cap(), 2^20 since Review-2026-11-17 #11). view_apply_size_hints() then returns w = INT32_MAX. With tiling on, tile.c:133 min_frame() computes cw + frame_extra_w(view), which is signed overflow: UB that UBSan flags, and in practice a negative width. The window then counts as fitting its cell (fw > mw is false). view_apply_tile() (view.c:782) overflows again in r.x + r.width - (w + frame_extra_w(view)) and puts the window near x = -2^31, off every output, where the frame and hit-test sums overflow further. Without tiling, an outline resize does the same: input.c:453 gives cw = INT32_MAX, and show_outline() adds frame_extra_w (input.c:160). Maximize sends a configure of INT32_MAX (view_fit_state, view.c:500).

   [Suggested: Clamp the xdg limits the way X11 and the geometry already are: in read_xdg_size_hints() cap min_width/min_height and max_width/max_height at VIEW_MAX_SIZE (move the define into mwc.h or add a shared size_cap), keeping 0 as 'no limit'. Add a crash.sh case where xdgc sets min_size INT32_MAX with tiling on and does an outline resize under UBSan.]

16. **Closing the shown tab of a group takes the keyboard from an on-demand layer surface (review item 9 missed this path).** `src/tabs.c:183`, focus, confidence high.

18. **Every set_title redraws the title strip at once, with no throttle.** `src/view.c:1017`, hostile, confidence medium.

   wlroots emits set_title for each xdg_toplevel.set_title request, outside any commit (wlr_xdg_toplevel.c:203-223), and Xwayland does the same for each WM_NAME/_NET_WM_NAME PropertyNotify. view_update_title() skips only an identical title. For any other title, frame_render_title() -> render_strip() allocates a new W x (B+T) cairo image, paints the whole frame through the clip, lays the title out with Pango and replaces the scene buffer. A client, or a program inside a terminal that forwards OSC 0/2 titles (a progress counter, `cat` of a file full of title escapes), can send thousands of distinct titles in one burst. mwc then does thousands of allocations, paints and Pango layouts in one dispatch, up to 32767 x 28 x 4 = 3.7 MB each for a wide window, and the whole session stalls. Each frame shows only the last one. The 2026-11-17 review throttled move feedback (item 7), struts (8) and desktop switches for the same reason; titles were left out. xw_set_class/xdg_set_app_id have the same pattern with tile_arrange and a full frame_render per distinct app_id, but that is less realistic.

   [Suggested: Store the title as now but route the redraw through a per-view `struct throttle` (16 ms, leading edge, as for feedback/arrange), so at most one strip render per refresh draws the latest title. An icon label re-render can share it. Test: an xdgc mode setting N distinct titles in a burst, with a draw counter in the test state, as move.sh checks `draws`.]

19. **outputMode parsed with %d and no upper bound, the flaw review item 13 fixed for outputPosition.** `src/main.c:393`, hostile, confidence high.

   configure_mode() reads WIDTHxHEIGHT with sscanf("%dx%d"). A value past INT_MAX is undefined behaviour; glibc truncates, so `Mwm*HEADLESS-1*outputMode: 4294967301x1080` becomes 5x1080, the same symptom item 13 fixed for outputPosition. On a backend without a mode list (headless, which the RDP/VNC setups use, and nested), any positive w/h goes straight to wlr_output_state_set_custom_mode. `100000x100000` makes mwc's shm allocator posix_fallocate a 40 GB memfd. A width near INT_MAX breaks the assumption behind outputPosition's ±1e6 limit ('keeps sums of positions and sizes from overflowing'): box.x + box.width sums in layer.c/view.c overflow. `@1e10` makes `(int)(hz * 1000)` (lines 401 and 409) an out-of-range float-to-int conversion (UB, not caught by -fsanitize=undefined). The fuzz harness covers only config.c, so main.c's output parsers are not fuzzed.

   [Suggested: Parse with strtol like outputPosition: check end pointers, limit w/h to a sane maximum (e.g. 1..32767, the most a cairo/GL buffer can be anyway) and hz to (0, 1000], then convert. Add the bad values to session.sh next to the outputPosition case.]

20. **wlroots 0.19.3 is already out with the fixes mwc waits for, and with a crash fix for virtual pointers; TODO credits them to 0.20.2.** **checked** `TODO:54`, nohacks, confidence high.

   The rule is no workarounds for fixed bugs: wait for the release. TODO:54 and TODO:67 say that 0.20.2 brings the capture-source fix and the allocator fix, and tie both to a full API migration from 0.19 to 0.20. Tag 0.19.3 in ~/data/src/wlroots already has both: 0f9a1f1 'image_capture_source/output: Update constraints on enable' (exactly the wayvnc-during-DPMS bug in TODO:45-63) and 4279ee5 (the shmalloc bug). It also has 878aebf 'wlr_virtual_pointer: Set axis source on all axis'. With MWC_VIRTUAL_INPUT=1 on 0.19.2, a virtual-pointer client can send axis_source(finger), then axis(vertical), axis(horizontal) and frame.
