# Review 2026-11-19b

Three reviewers on fix/x11-geometry at cb3c845: the size mwc keeps for X11 windows, the anchoring of a resize from the left or top, the layout comparison and the tests. One verifier. 10 findings, all confirmed, most from one cause: view->x stayed at the old place while a new size was on its way, and whatever paired it with requested_w/h sent X a wrong position.

## Status

All points settled on fix/x11-geometry. Each fix with a test that fails without it, checked by taking the change out, except where the point says otherwise.

1. **X11 anchor is dropped by a commit at the old size, so the last size after a left or top drag lands unanchored** `src/xwayland.c:76`, requested, medium. (#0)

   An X11 window that keeps redrawing (xterm with a blinking cursor, mpv, glxgears) is dragged by its left edge. The grab ends on release while the last configure B is still in flight: configure_pending is true, anchor_edges is LEFT, and view->x = x_A for the committed width A. Before Xwayland processes B, a commit at the old width A arrives. That can happen, as the xw_commit comment says: a frame drawn before the configure. xw_size_committed is skipped because the size equals view->width, xw_commit clears configure_pending, and with !grabbed && !configure_pending it sets anchor_edges = 0. Commit B then reaches xw_size_committed with no anchor, so view->x stays x_A and the width becomes B. The right edge moves by B-A after the drag. X was told x_B + frame_left with B (view_send_geometry), so the X window position and the frame disagree by A-B until the next move. Override-redirect menus of the client open shifted by that much. On main, X11 always set view->x together with the size, so the final state was consistent. The xdg path clears the anchor only on a matching ack serial, so it does not have this problem.

   [Fixed: the anchor goes only with a commit at the size last sent (requested_w/h), not with configure_pending. No test: a commit at the old size after the configure is a race.]

2. **While an anchored X11 size is in flight, configures pair the committed-size x with the requested size and leave X's position wrong** `src/xwayland.c:44`, requested, medium. (#1)

   During a left-edge resize, view_send_geometry sends (x_B, B) but leaves view->x at x_A, which belongs to the committed size A. Three paths then send view->x together with requested_w = B. (1) The correction in xw_size_committed: a stale commit at A arrives after B was sent. This happens when an old-size commit cleared configure_pending and B followed. The handler anchors view->x = x_A, sees A != requested B and sends (x_A + frame_left, B). (2) xw_request_configure while grabbed (line 356): view_send_size(requested) becomes view_send_geometry(view->x = x_A, B). This happens when a client sends a ConfigureRequest mid-drag. (3) xwayland_configure via view_frame_changed: a reload during the grab sends (x_A, B). Reloads now keep the grab alive. X queues these after (x_B, B), so the X window ends at x_A + frame_left with width B. When B commits, xw_size_committed sets view->x = x_B, but current == requested, so no configure corrects X. The X window believes it is B-A pixels away from where it is drawn. Client-placed override-redirect menus (Motif pulldowns in nedit or xmgrace) and root coordinates stay off until the window is moved again. On main, X11 resizes set view->x with the size, so these paths sent consistent geometry.

   [Fixed by a change of design: view->x and y are now where the size last sent goes, as X is told (view_send_geometry()), and only the scene node stays at the anchored place of the size the window has (view_place_x11_frame()). What sends X a position with requested_w/h is consistent again. The correction in xw_size_committed() is gone. No test of X's own idea of the position.]

3. **After a left-edge grab ends with a size in flight, a size-only ConfigureRequest pins the frame at the old x** `src/xwayland.c:363`, requested, low. (#2)

   A left-edge drag of an X11 window ends without apply. Configure B is in flight, anchor_edges is LEFT and view->x = x_A. The client then sends a ConfigureRequest with only a size, as clients do that answer a ConfigureNotify by asking again for their size. Because view->x and requested_w disagree, the request counts as 'no new place': vx/vy equal view->x - fx0, so fx = x_A. view_set_geometry(x_A, ..., w) clears the anchor, and the window keeps the left edge of the old size: the right edge jumps by w-A. The X window is moved back from x_B to x_A. On main the X11 grab had already set view->x = x_B, so the right edge stayed. A new grab started right after (view_begin_interactive builds grab_geobox and anchor_right from view->x = x_A with width requested B) shifts the anchor by B-A in the same way.

   [Fixed by a change of design: view->x and y are now where the size last sent goes, as X is told (view_send_geometry()), and only the scene node stays at the anchored place of the size the window has (view_place_x11_frame()). What sends X a position with requested_w/h is consistent again. xw_request_configure() and view_begin_interactive() pair view->x with requested_w/h, which now belong together.]

4. **anchor_edges is cleared by a commit that does not answer the last configure, so the grab's final size commits unanchored** `src/xwayland.c:76`, anchor, medium. (#3)

   Opaque resize of an X11 window from the left edge. Size A is committed (Xwayland's first commit), and grab_resize_caught_up sends B with B's position through view_send_geometry; view->x stays at A's place. The user releases right away. grab_resize_waiting is false, so end_grab does not apply and anchor_edges stays set. Before X has handled B, a commit at the old size A arrives: the client's own redraw after Xwayland's background commit (the double commit the test notes), or a blinking cursor (Emacs, Qt) or other drawing. xw_commit treats any commit as answering the configure and clears configure_pending; the window is no longer grabbed and nothing is pending, so it clears anchor_edges. The commit of B then reaches xw_size_committed with no anchor, so view->x stays at A's place with width B. The right edge ends up B-A px off for good, and X thinks the window is at B's position while the frame sits at A's. On main, view_set_geometry had already set x for B, so the final geometry was right. The same happens if the pointer goes back to the committed size: view_send_geometry then leaves configure_pending false although A is still in flight.

   [Fixed with #0.]

5. **The reconfigure for a size other than requested sends B with A's position and overrides B's correct position** `src/xwayland.c:44`, anchor, medium. (#4)

   During a fast left-edge resize, a commit at the old size clears configure_pending while A is still in flight, and resize_to sends B at B's position (b->x). The commit of A then arrives: xw_size_committed anchors view->x for A, sees A != requested B, and sends X the position anchor_right-(A+extra)+frame_left with size B. X handles the correct configure for B first, then this one, so the window ends at A's x. When B commits, current == requested, so nothing corrects it: the frame is at B's place and X believes the window is at A's, off by B-A px. If B was the last size of the grab, this stays until the next move. X clients compute root coordinates from that position, so override-redirect menus (xterm Ctrl+click, Motif popups) open B-A px away from the pointer, and XTranslateCoordinates or xdotool report the wrong place.

   [Fixed with #1: the reconfigure is gone.]

6. **During a grab, configures built from the stale view->x move the X window back to the frame's old place** `src/xwayland.c:358`, anchor, low. (#5)

   While a left-edge resize grab waits for size A (frame and view->x still at the old place, X already told A's position), the client sends a ConfigureRequest. Xt and Motif shells and Java AWT do this in reaction to a resize. xw_request_configure takes the grabbed branch and calls view_send_size(requested_w, requested_h), which is view_send_geometry(view->x, ...) with the old x and size A. X now has the old left position with the new size. When A commits, the frame is anchored to A's position but current == requested, so X is not told, and the X window position and the frame disagree by A-O px until the next configure, or permanently if A was the last size. On main, view->x had already moved with view_set_geometry, so this was consistent. view_frame_changed -> xwayland_configure during the grab does the same: a reload, which now keeps the grab and goes through view_theme_changed, or a hints or decor change.

   [Fixed by a change of design: view->x and y are now where the size last sent goes, as X is told (view_send_geometry()), and only the scene node stays at the anchored place of the size the window has (view_place_x11_frame()). What sends X a position with requested_w/h is consistent again.]

7. **When a waiting size is applied at release, the opposite edge still jumps for X11** `src/input.c:221`, anchor, low. (#6)

   Opaque left-edge resize of a slow X11 client. At release a size is still waiting (grab_resize_waiting) because A has not committed. end_grab calls clear_grab and then resize_to, which, no longer grabbed, takes view_set_geometry: anchor_edges = 0, the node moves to target.x at once and T is sent. Until T commits, the frame is at T.x with the old width or A, so the right edge jumps by T-A. When A commits it is unanchored, so the jump stays until T arrives. This is the TODO defect the commit message says is fixed 'also for the last size of a grab that has just ended'. The new move.sh test releases only after SIGCONT and the commit, so it does not cover this. For xdg the same path keeps the anchor (view_send_size).

   [Fixed: resize_to() sends X11 the geometry anchored also after the grab. move.sh: released with Xwayland stopped and a size waiting, the right edge stays.]

8. **A stale anchor_edges from an earlier left-edge grab is applied to a later size change sent through view_send_size** `src/tabs.c:241`, anchor, low. (#7)

   An X11 window W is the shown tab of a group with V. W is resized from its left edge, and the user releases once it has caught up (no apply, configure_pending false). W is idle (xterm without cursor blink commits nothing), so anchor_edges=LEFT stays set, because only xw_commit clears it. Later V's client exits while V is hidden (or V is dragged out). The group ends, back_to_own_size(W) calls view_send_size(W, own_w, own_h), which does not reset anchor_edges, and the commit of the new size goes through xw_size_committed with the old anchor. W keeps its right edge and moves its left edge, where on main its left edge stayed. Whether this happens depends on whether W committed anything in between. view_send_size calls from tabs_sync_sizes, xw_request_configure for maximized or docked windows and view_decoration_changed have the same exposure.

   [Fixed: view_send_size() outside a resize grab drops what is left of an anchor. No test: it needs an idle client and a later size change through tabs or the dock.]

9. **X11 left/top resize: a configure sent before the commit puts X back at the old x, and nothing corrects it** `src/view.c:177`, layout, medium. (#8)

   Between view_send_geometry() and the matching commit, view->x is still the x from before the resize. Two paths send X a configure from that stale x in this window. (a) The X client sends a ConfigureRequest. xw_request_configure() takes its grab branch: view_send_size(requested_w, requested_h) -> view_send_geometry(view, view->x, ...). (b) A reload. The grab now survives it because layout_moved() is false, and config_reload() -> view_theme_changed() -> view_frame_changed() -> xwayland_configure() sends view->x + frame_left with requested_w. Either way X ends up at x_old with w_new. The commit then arrives, and xw_size_committed() moves the frame to anchor_right - w_new. Its corrective configure only goes out when s->current differs from requested, and here they are equal, so X keeps x_old. Concrete case: an X11 window at x=200, w=300, dragged from its left edge to w=350, with a reload or a ConfigureRequest after the last configure and before its commit, then the button released. The window is drawn at x=150, but X and the client believe it is at 200. The client's override-redirect menus and tooltips land 50 px off until the next move. On main, view_set_geometry() set view->x first, and a reload ended the grab, so this could not happen.

   [Fixed with #1.]

10. **A failure while Xwayland is SIGSTOPped leaves a stopped Xwayland behind** `tests/move.sh:442`, layout, low. (#9)

   Between `kill -STOP $XW` (line 440) and `kill -CONT $XW` (line 445) the test calls `check "the pointer is there"` and `refresh`. Both can call fail(), for example on a regression where mwc makes a synchronous X round trip during the resize, or on a slow machine where 100 x 20 ms is not enough. fail() exits, and cleanup() kills mwc and sends SIGTERM through kill_leftovers. A stopped process only receives SIGTERM once it is continued, and wlroots does not kill Xwayland, it relies on a broken pipe. So that Xwayland stays stopped for good, holding its /tmp/.X11-unix socket and lock in the shared distrobox, and every failing run adds one.

   [Fixed: tests/lib.sh continues CONT_ON_EXIT on exit; move.sh sets it while Xwayland is stopped.]
