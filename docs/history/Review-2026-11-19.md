# Review 2026-11-19

Nine reviewers on fix/x11-focus at bef261d, one lens each: the map decision, FocusIn, unmap, fullscreen and activation, wlroots' xwm, completeness, the tests, xclient, docs and rules. Three more tried to refute each finding. 25 findings, 17 confirmed, 8 refuted.

## Status

All points settled on fix/x11-focus. Each fix with a test that fails without it, checked by taking the change out, except where the point says otherwise.

Found on the way: wlroots 0.19.2 sends WM_TAKE_FOCUS to a window with the input hint
with the event mask SubstructureRedirect (xwm_focus_window()), so only a client selecting
that on the window gets it, and none does; for one without the input hint it sends only
WM_TAKE_FOCUS and leaves the X focus alone. So mwc setting the focus back loops only
with a program that passes the focus on whenever its window gets it, as Java does with a
modal dialog: xclient's modal=1 does that, and the tests in window.sh use it.

## Confirmed

1. **WM_TAKE_FOCUS guard hands off to view_focus() for an icon, a hidden dialog or a hidden tab, which takes the keys from the launcher** `src/xwayland.c:524`, wlroots, high. (#8)

   A program with WM_TAKE_FOCUS that answers it Java-style (like xclient take_focus=1) has main window M activated under an on-demand launcher. Its dialog D was minimized on its own (or D is a hidden tab in M's group). minimize only sets WM_STATE in wlroots and leaves the X window viewable, so XSetInputFocus(D) works, and the same-pid rule (xwm.c:1886) emits focus_in. First FocusIn D: refused, activate(M,true) sends WM_TAKE_FOCUS to M, x11_refocused=M. The program answers by focusing D again. Now x11_refocused==focused, so view_focus_instead(D) runs. Its check at view.c:469 sees D->minimized (or tab_hidden or hidden_with_parent) and calls view_focus(D). view_focus calls view_restore, which calls view_focus again; that sets focused_layer=NULL and calls input_keyboard_enter. The X program brings back its icon and takes the keyboard from the launcher, which is the thing the branch is meant to prevent. A hidden tab goes through tabs_bring and the same from_layer path.

   [Fixed, see #2.]

2. **Unfocused map also skips the raise: a re-shown window or reused dialog lands under its parent and other windows** `src/view.c:1639`, map-decision, medium. (#0)

   view_handle_map() now returns on !focus before view_raise(). That means a window mapped without focus is never restacked, and its scene node keeps the position it had when view_init_common() created it or when it was last raised. wlr_scene_node_reparent() to the same parent is a no-op, so views_update_layers() does not move it either. Case 1: an X program has main window M and a dialog D it reuses (Motif/Xt XtManageChild, Tk deiconify, Java). D was shown and withdrawn once, then the user clicked M, which raised M above D's stale node. Later a Wayland terminal has the keys and the program maps D again, or maps a dialog it created at startup. In xw_map, focus=false because xwayland_may_take_focus() is false, so D maps below its own parent with no attention mark. This breaks the 'dialogs stay above the window they belong to' invariant: D stays invisible until the user happens to click M. Case 2: the user clicks a tray icon (SNI in a Wayland panel, or xembed in a docked X panel; neither moves the keyboard) to bring back a withdrawn X main window while a Wayland window is focused. been_mapped is set, so focus=false, and the follow-up _NET_ACTIVE_WINDOW is refused. The window the user asked for comes back buried under whatever covers it, with no visible change. On main it was focused and raised. The early return also stops a re-shown WT_SPLASH or docked window from being raised, though raising either takes no keyboard. The TODO item this branch closes said 'Für been_mapped höchstens anheben oder markieren'; neither is done.

   [Fixed: a window mapped without the focus is raised (view_handle_map()). window.sh checks that a window shown again and a new dialog are in front.]

3. **Follow path takes the keys from an on-demand launcher when the target window is an icon, a hidden tab or a dialog hidden with its icon** `src/xwayland.c:524`, focus-in, medium. (#2)

   An on-demand launcher (focused_layer set, exclusive_layer NULL) has the keys, and X window W1 of a program is activated below it. W2 is another window of the same pid that is minimized, or tab_hidden, or hidden_with_parent. Minimized windows stay mapped in X, because view_show() only disables the scene node and sets WM_STATE, so the program can SetInputFocus on W2. First FocusIn(W2): refused, W1 refocused, x11_refocused = W1. The program answers WM_TAKE_FOCUS by focusing W2 again. Second FocusIn(W2): view_focus_instead(W2) sees v->minimized, v->tab_hidden or v->hidden_with_parent and falls through to view_focus(W2). That calls view_restore() (or tabs_bring), then view_focus() again with from_layer true: focused_layer = NULL and input_keyboard_enter(W2). The launcher loses the keyboard and an icon is restored by the program, which is exactly what this branch is meant to prevent. Before the branch the launcher case always refocused W1.

   [Fixed: mwc follows only to a window in sight that takes input; otherwise it takes that window's X focus away. window.sh: the same program with its dialog an icon, under a launcher.]

4. **Following a non-focusable X window leaves mwc's active window and X focus apart once the launcher closes** `src/xwayland.c:524`, focus-in, medium. (#3)

   A launcher has the keys and W1 is activated. The program moves the X focus twice to its window W2, whose input model is NONE (input=0, no WM_TAKE_FOCUS, e.g. a palette). X lets a client SetInputFocus on it whatever the hints say. On the second FocusIn, view_focus_instead(W2) finds !view_focusable and calls view_focus(W2), which only raises W2 and returns. W1 stays activated in mwc, but wlroots' focus_surface and the X server focus are W2. When the launcher closes, take_keyboard_back() calls view_focus(W1). W1 is already activated, so view_set_activated is skipped and wlr_xwayland_surface_activate(W1) is never sent. Xwayland routes the keys to W2 while W1 is drawn as active. The old code always refocused W1 here, so this divergence is new in the launcher case.

   [Fixed with #2, and view_focus() activates an already active X11 window in wlroots again, so the X focus comes back when the launcher goes. window.sh checks the program is offered the focus again then.]

## Refuted

   [Refuted: This follows the branch's own policy rather than breaking it. The dialog revealed by withdrawing its icon gets the same treatment. Before the branch it took the keys from the launcher, which is the thing the branch prevents. Ending up with no focus after the launcher closes is consistent with the shown-again case, not a defect.]

18. **A refused X11 fullscreen of an 'above' window covers the focused Wayland window** `src/view.c:906`, fullscreen-activate. (#7)

   [Refuted: own_layer() is right that an unfocused fullscreen 'above' window lands in VL_ABOVE and covers the output. 19. **Refusal to a globally active (input=0) window does not move the X focus back** `src/xwayland.c:528`, wlroots. (#10)

20. **WM_TAKE_FOCUS ping-pong still unbounded for a window on another desktop** `src/xwayland.c:521`, wlroots. (#11)

## Second round

Four reviewers on de28b4e (bef261d..de28b4e), one lens each: the X11 reactivation in view_focus(), the map without focus, FocusIn and desktop_recheck(), the tests. One verifier. 8 findings, all confirmed; numbered S-0 to S-7. Each fix with a test that fails without it, checked by taking the change out, except where it says otherwise.

S-0. **xw_focus_in again lets an X11 program take the keyboard from a Wayland window or the icon box when wlroots' X focus is on another window of the same program** `src/xwayland.c:515`, reactivate, medium.

   de28b4e removes the xwayland_may_take_focus() check from xw_focus_in. Its reasoning is that wlroots lets no FocusIn through while a Wayland window or the icon box has the keys, because the X focus was taken away. That only holds if wlroots' focus_surface equals the X11 view mwc has activated. The comment the same commit adds in view_focus() says this is not always so: the program can move the X focus to a window mwc refused or has not mapped. view_set_activated(prev, false) calls wlr_xwayland_surface_activate(prev, false), which does nothing when focus_surface != prev (xwm.c:2102-2108). Concrete case: X11 main window A is activated. The same program maps a managed window M of type POPUP_MENU, DROPDOWN_MENU or COMBO (WT_NOTIFICATION, so !view_focusable), or a window with input model NONE, and calls XSetInputFocus(M). Steam's non-override-redirect menus are the case behind wlroots' same-pid rule (sway#1865). wlroots sees the same pid and sets focus_surface = M. xw_focus_in(M) calls view_focus(M), which only raises it, so A stays activated. M then unmaps or stays open. Unmap does not clear focus_surface, and view_handle_unmap only deactivates when was_active is set. The user clicks a Wayland window W (or the icon box takes the keys). view_set_activated(A, false) is a no-op in wlroots, and focus_surface stays M. Later the program focuses any of its windows C, for example its main window or a chat window. The FocusIn passes the same-pid check. In xw_focus_in, C is mapped and not activated, there is no focused_layer and C is not off_desktop, so view_focus(C) takes the keyboard from W. With bef261d, xwayland_may_take_focus() was false here, so the refusal branch ran activate(C, false), which cleared the X focus (focus_surface == C by then). The review fix for point 100 therefore removes protection that was actually reachable. A test cannot catch this, because xclient's windows are always focusable and in sync.

   [Fixed: xw_focus_in() refuses again while a Wayland window or the icon box has the keys, as at bef261d; the premise in de28b4e's comment was wrong. window.sh: a program moves the X focus to its own window without input, a Wayland window takes the keys, the program's next move doesn't take them.]

S-1. **A dialog mapped without the focus in a hidden tab of a group that is not an icon stays out of sight with no mark, and is not focused when its tab is chosen** `src/view.c:1627`, map-raise, medium.

   An X11 program has tabs A (shown, activated) and B (hidden) in one group, not minimized. Either a Wayland terminal has the keys, or an on-demand launcher is open over A (the new tabs.sh case). B maps a modal 'save changes?' or password dialog D, so xw_map gives focus=false. tabs_bring() is now skipped, and hide is true because B is tab_hidden, so D gets hidden_with_parent=true and view_show(D,false), followed by the early return. Nothing marks it: desktop_attention() only applies off_desktop, the icon box lists no hidden_with_parent windows, cyclable() excludes them from Alt+Tab, and the tab bar has no attention state. When the launcher closes, take_keyboard_back() focuses A and D stays invisible while the program blocks on it. tabs_after_restore() picks up such a waiting dialog only when the group was an icon, which is not the case here. When the user eventually clicks tab B, switch_to() runs dialogs_show(B,true) and then view_focus(B): D becomes visible, but the keys go to B, not to the dialog. A GTK or Motif modal dialog then ignores the typing. That differs from the restore path, which calls view_focus(d) on the waiting dialog. On main the tab came to the front and D got the focus. At bef261d the tab came to the front without the focus, so D was at least visible. The tabs.sh test only checks the moment under the launcher, not what happens after it closes.

   [Fixed: refused, the dialog still brings its tab to the front, without the keys (tabs_bring_instead()), and if its window has the focus under a launcher, the dialog has it below the launcher and gets the keys when it goes. tabs.sh: under a launcher, and with a Wayland window outside the group focused.]

S-2. **The !focus raise in view_handle_map does not refresh the pointer, so the window under the cursor keeps pointer focus until the mouse moves** `src/view.c:1658`, map-raise, low.

   A Wayland terminal T has the keys, and the cursor rests over T. An X11 program shows its withdrawn main window W again, for example from a tray icon, at a place that covers the cursor.
